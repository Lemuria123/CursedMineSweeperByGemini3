# 开格重排算法

开格时的诅咒和祈祷都走 `shared/gameLogic.ts` 里的 `rearrangeMines`。前端和服务器复盘共用这一份代码，以及同一个 `mine_seed + '-csp'` 种子。首击布雷 `placeMines` 没有改，仍是均匀抽雷。

## 1. 三条不变量

顶栏剩余雷是 `难度雷数 - 已插旗数`。重排只要成功返回，就必须同时满足：

1. 全盘 `isMine` 的个数与进入函数时相同。
2. `status === 'flagged'` 的格子不改变 `isMine`。
3. 已翻开格子的 `neighborMines` 仍等于周围真实雷数，并且与进入时的数字相同。

任何一条做不到，就恢复进入时的 `isMine` 和 `neighborMines`，函数返回 `false`。诅咒失败时格子保持原样再翻开；祈祷快速搜索失败时，用原棋面进行全盘精确求解。

局部重排先用「不挨着已翻开格子」的隐藏格补平雷数差额：

- 这一步雷变多：只能关掉同样多的孤立雷。
- 这一步雷变少：只能把同样多的孤立安全格改成雷。

诅咒在孤立格补不平时整步放弃。祈祷快速搜索若无法配平，转入全盘求解。重排成功时总雷数必须与原来一致。

## 2. 求解

目标格如果已经插旗，雷位钉死，不能翻。

没有已翻开约束时直接交换：诅咒把目标格和一颗孤立雷对调；祈祷走第 3 节的抽样。邻居一旦挨着已翻开数字，就改走约束求解。

局部约束求解先处理目标格所在的一块。从目标格出发，沿着已翻开格子收集尚未翻开、也没插旗的邻居，上限 50 格。祈祷按数字偏好搜索该前沿，最多展开 3000 个分支。前沿截断、雷数无法配平或预算耗尽时，只要快速搜索没有找到合法摆法，就从开格前的棋面启动 Worker。

每个已翻开数字是一条等式：周围雷数必须仍是原来的数字。求解前先做强制传播：数字已经凑满，未定邻居全是安全；还缺的数量正好等于未定邻居数，那些邻居全是雷。传播不动后再用堆上的显式栈回溯，调用栈保持常数层。单次诅咒最多展开 4000 个分支，祈祷快速搜索最多展开 3000 个分支。

每次快速祈祷失败都触发全盘兜底。求解器固定目标安全、旗子原雷位和公开数字，将受完全相同数字约束的隐藏格合并为一组。每组的变量是雷数，从零到组内格数。全部自由格也合并为一组。

求解器先把共享未知格的公开数字等式两两相减，消去共同项。它在原等式和差式上收紧各组雷数的上下界。如果等式所需雷数超出可取范围，就证明目标无法安全翻开。否则丢弃预检查的临时上下界，回到原始变量范围，加入全盘剩余雷数等式，按原顺序用显式栈回溯。找到可行布局就恢复具体雷位，所有分支都出现矛盾才爆炸。预检查和兜底搜索均不消耗随机数。

浏览器通过模块 Worker 执行兜底。重新开局会取消等待，Worker 出错可在原棋面重试。新录像使用版本 3。版本 1 和 2 仍按原 6000 分支、前沿重试与跨块补偿重放；版本 2 会在快速搜索失败后继续精确求解。

泛洪在 `revealCellFast` 里，本身就是堆数组。入栈前先标记，同一格不会从多个空邻居被重复推进。

## 3. 祈祷时的数字

数字永远等于周围真实雷数，不把抽到的整数直接写进格子。

只有 `forceMine === false`、目标格最终是安全格时才抽样。诅咒只尝试把该格变成雷，不为它抽一个数字。

设全局雷密度 `p = 雷数 / 总格数`，该格实际邻居数为 `d`（边缘不到 8）：

- `μ = p × d`
- `σ = sqrt(d × p × (1 - p))`
- 权重 `w(k) = exp(-(k - μ)² / (2σ²))`，`k` 落在不破坏第 1 节的闭区间里

用传入的 `rng` 按权重排出尝试顺序（`key = -ln(U) / w(k)`，key 越小越先试）。前 3000 个分支按这个顺序找「周围恰好 k 颗雷」的摆法。快速搜索失败后，全盘精确求解接受任意合法数字。写回后用周围真实雷数回填 `neighborMines`。

σ 接近 0 时，权重集中在离 μ 最近的整数上。

## 4. 不在这次范围内的行为

首击的 3×3 安全区和均匀布雷不变，所以第一下翻开的数字分布仍由 `placeMines` 决定。

服务端成绩校验和管理页回放根据录像版本选择开格规则，并从相同的种子恢复随机数序列。

## 5. 如何核对

在 `server` 目录执行：

```powershell
npx ts-node --transpile-only src/test_csp_invariants.ts
```

脚本覆盖补不平时的回滚、总雷数、插旗格、已翻开数字、同一种子两次结果一致、祈祷数字落在可行区间并等于回填值，以及 25×25 贴边重排。固定种子回归覆盖数字兜底、跨块补偿和前沿重试漏解，包括从 10,000 局批次中确认的七个漏解。

## 6. 浏览器本地重排统计

在游戏页面的开发者工具控制台查看当前浏览器的累计次数：

```js
console.table(JSON.parse(localStorage.getItem('cms_rearrangement_stats_v1') ?? '{}'))
```

`curse` 和 `prayer` 分开统计。每次实际尝试搬雷计一次，和弦触发的多次重排各自计数。首击和无需搬雷的操作不计。用 `isolated_shortage / (attempts - success)` 可计算已确认的补偿不足占全部重排失败的比例。

`isolated_shortage` 只计实时搜索中已有证据确认目标能翻、且孤立格无法补平的失败。小块补偿救回的祈祷计为成功。`budget_exhausted`、`frontier_limit` 和 `unclassified` 分别表示局部搜索预算耗尽、前沿截断及其余未确认原因。统计不会为未确认的情况再搜索，所以已确认的比例是下限。计数只保存在当前浏览器与站点地址下。
